# 対外発表前チェック

## 使い方

まず**発表の種類と日程**を聞く。種類によって逆算が変わる。

| 種類 | 特に効く節 |
|---|---|
| 合同ゼミ（大阪大・一橋大・早稲田大） | §1, §2, §4 |
| 企業への提案 | §1, §2, §3, §4 |
| コンペ（日経ストックリーグ、資産形成アワード、プロネクサス懸賞論文、CFA Research Challenge） | §1, §2, §5 |
| PJ中間・最終発表（ゼミ内） | §1, §2 |

---

## §1 逆算スケジュール

**発表日から逆算する。日付を実際に埋めてユーザーに返す。**

| 期限 | やること |
|---|---|
| **D-30** | 発表する班を確定させる（合ゼミは特に遅れる。ゼミ長が議題に上げる） |
| **D-21** | キメヘンを最終確認（→ `hoda-kimehen`）。ここで軸がブレていたら間に合わない |
| **D-14** | **スライド初稿完成。**ストーリーラインではなく、実際のスライドまで |
| **D-10** | チーム内レビュー。ゼミ長・先生に一度見せる |
| **D-9〜D-7** | **提出物の締切**（合ゼミは事務局提出が発表の1週間以上前にあることが多い。例：11/30開催に対し11/21金までに提出） |
| **D-7** | **リハーサル1回目**（通しで、時間を計る） |
| **D-3** | 想定質問への回答準備完了 |
| **D-2** | **リハーサル2回目**。ここで直すのは表現だけ。中身は変えない |
| **D-1** | 印刷・機材・持ち物の確認。データのバックアップ |

**D-14でスライド初稿ができていないなら、その時点で主張を減らす判断をする。**間に合わないまま突っ走るのが最も評価を落とす。

## §2 中身のチェック

- [ ] **キメヘンの表が埋まっている**。聞き手ごとに、メッセージと起こしたい変化が書けている
- [ ] 全スライドが、キメヘンのどれかの行に効いている。効いていないスライドは削った
- [ ] **メインメッセージがスタンスを取っている**。「〜という側面もある」で逃げていない
- [ ] 主張を裏付ける数字が全部ある。裏付けのない主張は削ったか、弱めた
- [ ] **全ての数字に出所がある**。一次情報（有報、短信、統合報告書、適時開示）に当たっている
- [ ] 単位が百万円で統一されている
- [ ] **企業価値向上と社会的価値向上の両立**に接続している。財務的に正しいだけの提案になっていない
- [ ] 定量インパクトの試算が入っている（この施策でROICが何pt動くか）
- [ ] 反証（何が起きたらこの結論が崩れるか）を自分で用意している

## §3 企業への提案の場合

- [ ] **提案先企業のロゴカラーを随所に仕込んでいる**（保田研の作法）
- [ ] 提案先の**直近の開示**（決算短信、中計、統合報告書、適時開示）を発表日の直前まで追った。発表当日に「先週出た開示を知らない」は致命傷
- [ ] 提案先の**社名・役職名・人名の表記**が正確。誤記は一発で信用を落とす
- [ ] 提案の意思決定者が誰かを特定し、その人が明日から何をするかまで書いた
- [ ] 提案先に不利益な内容（人員削減、事業撤退）を含む場合、緩和策とステークホルダーへの影響を併記した
- [ ] **非公開情報を扱っている場合**、開示可否を先生・先方に確認した

---

## §4 合同ゼミの場合

- [ ] 発表班が確定している（D-30）
- [ ] **事務局への提出物と締切を確認した**。pptxで提出か、pdfか、締切はいつか
  - 過去の運用例：各チームがpptxで提出 → 全チーム連結のpdf化はこちら側でやる
- [ ] 提出ファイル名の規約を確認した
- [ ] 発表時間・質疑時間を確認し、**時間内に収まることをリハで実測した**
- [ ] 会場の機材（HDMI／USB-C、スクリーン比率16:9）を確認した
- [ ] 移動・宿泊の手配が済んでいる（大阪開催なら特に）
- [ ] **他大学に渡す参加者リストに個人情報（学籍番号、メールアドレス）が入っていない**
- [ ] 英語話者メンバーへの情報共有ができている

---

## §5 コンペの場合

- [ ] **応募要項を最新版で読み直した**。書式・字数・ページ数・フォント・提出形式
- [ ] 提出期限の**時刻**まで確認した（23:59か17:00かで1日変わる）
- [ ] 参加資格（学年、所属、チーム人数）を満たしている
- [ ] 引用・出典の表記規約に従っている
- [ ] **提出前に別のメンバーが要項と照合した**。自分では見落とす

---

## §6 当日

### 準備

- [ ] 発表者の役割分担（誰がどのスライドを話すか）が決まっている
- [ ] **スライドの切り替えは、話していないメンバーが担当する**
- [ ] **質疑の担当が決まっている**（財務の質問は誰、戦略の質問は誰）
- [ ] 想定質問リストを作り、回答を準備した。特に **「なぜこのピアグループなのか」「なぜこの前提なのか」「実現可能性は」** は必ず来る
- [ ] **質疑応答時に見せる用のスライドを別途作成した**（Appendix）
- [ ] スライドのバックアップ（PDF版、別デバイス、クラウド）がある
- [ ] **最後のスライドに「これだけは覚えて帰ってほしい」を詰め込んだ。**「ご清聴ありがとうございました」スライドは作らない
- [ ] 時間を計る人を決めた
- [ ] **FBをメモする人を決めた（できれば紙とペン）**

### 話し方

- [ ] **書いてあることは読まない。**スライドに書いてあることをそのまま読み上げない
- [ ] **「わかりません」を避ける。**答えられない質問には「持ち帰って確認します」「現時点では〜と考えていますが、〜のデータを確認する必要があります」と返す
- [ ] **聞き手を想像して話す。相手がすでに知っていることをダラダラ説明しない。**提案先企業に、その企業の事業説明を長々とやらない

---

## §7 発表後（当日中にやる）

- [ ] **もらったフィードバックをその日のうちにテキスト化してSlackに残す。**記憶に頼らない
- [ ] 次回に向けて、対応するFBと対応しないFBを決めた
- [ ] （中間・最終発表の場合）**翌週の360°FBの準備をする**（→ `hoda-360-feedback`）
- [ ] 資料をDriveの所定の場所に置いた。ファイル名に日付と発表名を入れた
- [ ] **企業訪問・企業への提案の場合、感謝のメールを作成して送った**
